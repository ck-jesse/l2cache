# 缓存监控与管控 需求分析报告

## 1. 需求概述

为 L2Cache 增加缓存可视化监控与轻量管控能力：通过 Micrometer 埋点 + Prometheus 采集 + Grafana 展示核心缓存指标，并在 l2cache-spring-boot-starter 中暴露 HTTP 管控端点支持缓存列表查看、手动清除与一致性检测。

## 1.1 已确认信息

- **架构方向**：Prometheus 原生监控 + 嵌入 starter 的管控端点（排除独立 l2cache-server / 独立 l2cache-dashboard 前端项目方案）
- **首期范围（MVP）**：
  - 监控指标：命中率、穿透次数、缓存 QPS、缓存总数、缓存大小（占用内存）
  - 排行榜：热 key 排行榜、大 key 排行榜
  - 管控能力：缓存列表查看、手动清除指定缓存、一致性检测
- **指标粒度（两个维度）**：
  - 维度一：cacheName + 实例（instance_id）
  - 维度二：key + cacheName + 实例（instance_id）
- **监控链路**：l2cache-core 埋点（Micrometer）→ Prometheus 抓取 → Grafana 展示
- **管控承载**：l2cache-spring-boot-starter 暴露 HTTP 端点（Actuator 风格），纯 API 无前端页面
- **部署环境**：已有 Prometheus + Grafana 基础设施
- **后期方向**：后续迭代希望支持管理后台进行管控（本次不实现前端）
- **性能约束**：埋点不得降低缓存主流程性能（35W QPS 场景下额外开销可忽略）

## 1.2 待确认假设

- **大 key 判定标准**：假设按缓存值序列化后字节数判定，阈值可配置（默认如 1KB 以上纳入统计）。具体阈值与采样策略在技术方案中确定。
- **一致性检测范围**：假设检测同一 cacheName 在不同实例节点上的缓存数量与关键 key 差异，不要求强一致实时比对。具体检测方式在技术方案中确定。
- **管控端点安全**：首期不额外实现鉴权，复用应用现有安全体系；同时输出一份鉴权实现方案供参考。

## 2. 业务目标

- **主要目标**：让应用中的缓存状态可观测、可管控
- **预期价值**：从"缓存现状未知"到"有监控有方向"，支撑缓存治理决策
- **成功指标**：
  - Grafana 可展示核心缓存指标与热/大 key 排行榜
  - 可通过 API 查看缓存列表并清除指定缓存
  - 可通过 API 检测多节点缓存一致性

## 3. 用户场景

- **目标用户**：运维工程师、后端开发、架构师
- **使用场景**：线上缓存行为分析、缓存问题排查、缓存手动清除、多节点一致性核查
- **典型流程**：
  1. 开发接入 l2cache，自动埋点上报 metrics
  2. Prometheus 抓取 metrics，Grafana 展示命中率/QPS/穿透/热key/大key 等
  3. 排查问题时调用管控 API 查看某 cacheName 下的缓存列表
  4. 必要时通过 API 清除指定缓存
  5. 怀疑多节点不一致时调用一致性检测 API

## 4. 功能范围

### 核心功能

1. **l2cache-core 埋点**：
   - 缓存命中率、穿透次数、QPS、缓存总数、缓存大小（cacheName + 实例维度）
   - key 维度访问计数（key + cacheName + 实例维度），支撑排行榜
2. **热 key 排行榜**：基于 key 维度访问计数聚合，复用已有热 key 探测能力（JdHotkey/Sentinel）
3. **大 key 排行榜**：识别缓存值占用内存较大的 key
4. **l2cache-spring-boot-starter 管控端点**：
   - 缓存列表查询（分页）
   - 手动清除指定缓存
   - 一致性检测
5. **Grafana Dashboard 配置样例**：指标展示模板

### 功能边界

- ✅ 包含：核心指标采集与暴露、热/大 key 排行榜、缓存列表查看、手动清除、一致性检测、管控端点鉴权方案（参考性输出）
- ❌ 不包含（首期）：独立前端 dashboard、独立 server、配置动态修改、服务器内存统计

### 系统集成

- 复用 Micrometer + Prometheus + Grafana 体系
- 管控端点嵌入 starter，不新增独立服务

## 4.5 关键行为与边界

- **核心输入/输出**：
  - 输入：缓存读写操作（埋点触发）、管控 API 请求
  - 输出：Prometheus metrics 端点数据、缓存列表 JSON、清除/一致性检测结果
- **关键边界与异常**：
  1. 埋点失败必须静默降级，不得影响缓存主流程读写
  2. 管控清除操作需幂等，清除不存在的 key 返回成功
  3. 缓存列表查询需分页，防止大 cacheName 下返回过多数据
  4. 管控端点需可关闭（配置开关），不影响未启用监控的应用
  5. key 维度指标需控制基数，避免 Prometheus 标签爆炸（采用聚合或采样策略，技术方案中细化）
  6. 大 key 识别需异步或采样，不阻塞缓存读路径
  7. 一致性检测为轻量比对，不要求强一致实时同步
- **受影响的现有模块**：
  - `l2cache-core`：Cache 接口及实现（CaffeineCache、RedisCache、CompositeCache 等）需增加埋点
  - `l2cache-spring-boot-starter`：新增管控端点 Controller
  - 可能涉及 `L2CacheConfig`：新增监控与管控相关配置项
- **验收口径**：
  - 启用后 `/actuator/prometheus` 能看到 l2cache 相关 metrics
  - Grafana 能展示命中率/QPS/穿透次数趋势图 + 热key/大key 排行榜
  - 管控 API 能查询缓存列表并成功清除指定 key
  - 一致性检测 API 能返回多节点缓存差异结果

## 5. 技术约束

- **技术栈**：Java 17、Spring Boot 3.3.4、Micrometer、Prometheus、Grafana
- **性能要求**：埋点不得降低缓存主流程性能（35W QPS 场景下额外开销可忽略）
- **安全要求**：管控端点需可配置开关；鉴权复用应用现有体系，另输出鉴权方案参考

## 6. 资源与时间

- **时间要求**：待确认（首期 MVP）
- **人力配置**：待确认
- **预算限制**：无额外基础设施成本（复用已有 Prometheus/Grafana）

## 7. 风险与依赖

- **主要风险**：
  1. 埋点对高并发缓存路径的性能影响（需基准测试验证）
  2. 不同 Cache 实现（Caffeine/Guava/Redis/Composite）埋点方式差异，统一抽象有复杂度
  3. key 维度指标的高基数问题（Prometheus 标签爆炸风险）
  4. 大 key 识别的内存与性能开销
  5. 跨节点一致性检测的复杂度
  6. 管控端点的安全暴露风险
- **外部依赖**：已有 Prometheus + Grafana
- **应急预案**：埋点可通过配置全局关闭；管控端点默认关闭，按需开启

## 8. 实施建议

- **优先级**：高（第九阶段重点）
- **实施策略**：分阶段实施（先埋点+展示，后管控端点）
- **关键里程碑**：
  1. core 埋点 + metrics 暴露（含 key 维度聚合策略）
  2. 热 key / 大 key 排行榜
  3. Grafana Dashboard 样例
  4. starter 管控端点（缓存列表 + 手动清除 + 一致性检测）
  5. 管控端点鉴权方案输出
