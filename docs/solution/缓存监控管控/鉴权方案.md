# L2Cache 管控端点鉴权方案

## 1. 背景

L2Cache 管控端点（`/l2cache/manager/**`）支持查看缓存列表、清除缓存、热 key/大 key 排行、一致性检测等敏感操作。这些端点默认通过配置 `l2cache.config.metrics.management-enabled=true` 开启，开启后必须配合适当的访问控制，避免未授权访问。

## 2. 设计原则

- **默认关闭**：管控端点默认不启用，仅在需要时显式开启。
- **最小侵入**：首期不强制引入额外依赖或复杂权限模型，避免影响未使用管控功能的应用。
- **可扩展**：预留接口和扩展点，便于后期接入统一的管理后台。

## 3. 可选方案

### 方案 A：复用 Spring Security

**思路**：在应用已有的 Spring Security 配置中，针对 `/l2cache/manager/**` 路径配置角色权限，如仅允许 `ROLE_ADMIN` 访问。

**示例**：

```java
@EnableWebSecurity
public class SecurityConfig {

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http.authorizeHttpRequests(auth -> auth
            .requestMatchers("/l2cache/manager/**").hasRole("ADMIN")
            .anyRequest().permitAll()
        );
        return http.build();
    }
}
```

**优点**：
- 复用现有安全体系，无需额外开发。
- 与账号、角色、SSO 等能力天然集成。

**缺点**：
- 强依赖 Spring Security，未引入 Security 的应用需要额外配置。
- 灵活性受限于应用自身的安全策略。

**适用**：已有 Spring Security 且管理后台需要统一角色控制的场景。

---

### 方案 B：自定义拦截器 + Token 校验

**思路**：在 starter 中提供一个可选的 `L2CacheManagementInterceptor`，通过配置 `l2cache.config.metrics.management-token=xxx` 开启 Token 校验。请求头需携带 `X-L2Cache-Token`，校验失败返回 403。

**示例**：

```java
@Component
@ConditionalOnProperty("l2cache.config.metrics.management-token")
public class L2CacheManagementInterceptor implements HandlerInterceptor {

    @Value("${l2cache.config.metrics.management-token}")
    private String managementToken;

    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) {
        String token = request.getHeader("X-L2Cache-Token");
        if (!Objects.equals(token, managementToken)) {
            response.setStatus(HttpServletResponse.SC_FORBIDDEN);
            return false;
        }
        return true;
    }
}
```

**优点**：
- 不依赖 Spring Security，轻量可插拔。
- 适合服务间调用或简单管理脚本。

**缺点**：
- Token 需要集中管理，轮换成本较高。
- 无法与组织架构、角色权限体系联动。

**适用**：没有 Spring Security、但需要基础访问控制的场景。

---

### 方案 C：网络层隔离（推荐首期方案）

**思路**：管控端点仅暴露在内网，通过网关层（Nginx、Kong、Spring Cloud Gateway 等）做访问控制。应用侧不额外做鉴权，依赖网络边界安全。

**实践建议**：
- 生产环境将 `/l2cache/manager/**` 绑定到独立的内部端口或仅监听内网 IP。
- 通过 VPN、跳板机或办公网白名单访问。
- 配合网关的 IP 白名单、Basic Auth 或 OAuth2 做二次校验。

**优点**：
- 零代码侵入，对应用无依赖要求。
- 与现有运维体系（网关、防火墙）结合，实施成本低。

**缺点**：
- 无法做细粒度角色控制。
- 依赖网络边界安全，不适合多租户或复杂权限场景。

**适用**：首期 MVP、内网环境、运维人员少且信任边界清晰的场景。

## 4. 推荐结论

| 阶段 | 推荐方案 | 说明 |
|------|----------|------|
| 首期（MVP） | 方案 C：网络隔离 | 快速落地，零侵入，满足基本安全要求 |
| 中期（管理后台） | 方案 A：Spring Security | 接入统一权限体系，支持角色控制 |
| 特定场景 | 方案 B：Token 校验 | 轻量、独立，适合脚本或服务间调用 |

## 5. 后续扩展建议

- 在 starter 中预留 `@L2CacheManagement` 注解，标记需要鉴权的端点，便于后续统一接入。
- 提供 `L2CacheManagementSecurityConfigurer` 扩展接口，允许应用自定义鉴权逻辑。
- 考虑将管控端点迁移到 Actuator 端点体系（`/actuator/l2cache/**`），复用 Actuator 的安全配置。
