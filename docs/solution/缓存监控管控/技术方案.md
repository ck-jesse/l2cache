## 2. 方案设计

### 2.1 方案对比

#### 2.1.1 方案一：Micrometer 埋点 + 本地 TopN 聚合（推荐）

**核心思路**：cacheName 维度指标走 Micrometer 标签暴露给 Prometheus；key 维度（热key/大key）不走 Prometheus 标签，而是在本地内存维护滑动窗口 TopN 聚合，通过管控 API 暴露。

**优势**：
- cacheName 维度指标复用 Prometheus 生态，Grafana 原生支持
- key 维度用本地 TopN 避免 Prometheus 标签爆炸
- 埋点抽象解耦，core 不强依赖 Micrometer
- 一致性检测复用 Redis（L2）作为中介，不新增中间件

**劣势**：
- 本地 TopN 有一定内存开销（可控，仅保留 Top N 条）
- 一致性检测精度依赖上报频率

**适用场景**：高并发缓存框架的监控与管控

#### 2.1.2 方案二：全量 Prometheus 标签

**核心思路**：所有指标（含 key 维度）都通过 Micrometer 标签暴露给 Prometheus。

**优势**：
- 实现简单，统一走 Micrometer
- Grafana 可直接按 key 筛选

**劣势**：
- key 作为 Prometheus 标签会导致指标基数爆炸（数百万 key × 多指标）
- 严重违反 Prometheus 高基数标签最佳实践
- 对 Prometheus 存储和查询性能有严重影响
- 35W QPS 下标签创建开销不可控

**适用场景**：key 数量极少（< 1000）的场景，不适合本框架

#### 2.1.3 方案三：独立采集 Agent

**核心思路**：部署独立 agent 采集缓存指标，应用只暴露 JMX/HTTP 原始数据。

**优势**：
- 应用零侵入
- 采集逻辑独立演进

**劣势**：
- 违反最小实现原则，引入额外部署组件
- 与已有 Prometheus 基础设施不匹配
- 开发和运维成本最高

**适用场景**：无法修改应用代码的遗留系统

### 2.2 推荐方案：方案一

**选择理由**：方案一兼顾 Prometheus 生态兼容性与 key 维度高基数问题，不新增中间件，符合最小实现原则。

### 2.3 迭代影响

- **功能影响**：不影响现有缓存读写功能；埋点静默降级，失败不影响主流程
- **代码影响**：
  - `AbstractAdaptingCache`：在 get/put/evict 路径接入 MetricsRecorder 调用
  - `CompositeCache`：get 方法中 L1 命中/L2 命中/未命中埋点
  - `CacheManagerController`：扩展管控端点
  - `L2CacheConfig`：新增 Metrics 配置段
- **SQL/数据影响**：无（本框架无数据库）
- **依赖影响**：l2cache-core 新增 `micrometer-core`（optional），不影响未引入 micrometer 的用户

## 4. 技术要点

### 4.1 核心内容

1. **埋点抽象层 MetricsRecorder（Noop 设计）**：定义统一埋点接口，core 默认注入 `NoopMetricsRecorder`（空对象模式），starter 注入 `MicrometerMetricsRecorder`
   - **Noop 是什么**：Noop = No Operation（空操作），是空对象模式（Null Object Pattern）的实现。`NoopMetricsRecorder` 实现了 `MetricsRecorder` 接口，但所有方法的方法体为空（什么都不做）
   - **为什么零开销**：当用户未启用监控时，core 用 `NoopMetricsRecorder`。代码中虽然调用了 `metricsRecorder.recordHit(...)`，但实际执行空方法体，JVM 会内联优化掉（JIT 消除无效方法调用），几乎无性能损耗。相比每次调用前判空（`if (recorder != null)`），Noop 模式更简洁且无需分支判断
   - **替换机制**：启用监控后，starter 的 `MetricsAutoConfiguration` 通过依赖注入将 `NoopMetricsRecorder` 替换为 `MicrometerMetricsRecorder`，业务代码无感知
2. **cacheName 维度指标**：命中率、穿透次数、QPS、缓存总数、缓存大小，通过 Micrometer Counter/Gauge/Timer 暴露，标签 `cacheName` + `instanceId`
3. **key 维度 TopN 聚合**：本地内存维护滑动窗口计数器，按访问频次排序输出热 key，按 value 字节大小排序输出大 key
4. **一致性检测**：各实例通过 Redis 上报 L1 缓存快照（key 列表+数量），管控 API 比对差异
5. **管控端点扩展**：在已有 CacheManagerController 基础上新增缓存列表分页、一致性检测、排行榜查询端点

### 4.2 难易程度评估

- **简单**：cacheName 维度指标埋点（Micrometer 标准用法）、管控端点扩展
- **中等**：埋点抽象层设计、大 key 异步估算
- **复杂**：key 维度 TopN 滑动窗口聚合、跨节点一致性检测、35W QPS 下埋点性能保障

### 5.3 一致性检测触发机制序列图

**触发机制**：基于 Redis Pub/Sub（Redisson RTopic），复用已有 Redis 连接，不新增中间件。管控 API 发布检测任务到 `l2cache:consistency:channel`，各实例订阅该 Channel 实时响应，无需定时轮询。

```
运维/开发          管控API(实例A)         Redis Pub/Sub          实例A(本地)       实例B          实例C
  │                  │                      │                      │                │             │
  │ GET /checkConsis  │                      │                      │                │             │
  │   ?cacheName=xx   │                      │                      │                │             │
  │   &mode=value      │                      │                      │                │             │
  │   &keys=k1,k2      │                      │                      │                │             │
  │─────────────────▶│                      │                      │                │             │
  │                   │ 1.生成taskId         │                      │                │             │
  │                   │ 2.发布检测任务         │                      │                │             │
  │                   │─── PUBLISH ─────────▶│ l2cache:consistency:channel             │             │
  │                   │                      │─── 推送到所有订阅者 ──▶│                │───推送──▶│            │───推送──▶│
  │                   │                      │                      │                │             │
  │                   │ 3.等待各实例响应(2-3s)  │                      │                │             │
  │                   │                      │                      │                │             │
  │                   │                      │  4a.实例A计算本机k1,k2的valueHash(MD5)   │             │
  │                   │                      │  4b.写入Redis: result:{taskId}:instanceA│             │
  │                   │◀─── SET result ───────────────────────────────────────────────│             │
  │                   │                      │                      │  4c.实例B同理  │             │
  │                   │◀─── SET result ─────────────────────────────────────────────────────────────│
  │                   │                      │                      │                │  4d.实例C同理│
  │                   │◀─── SET result ─────────────────────────────────────────────────────────────────────────│
  │                   │                      │                      │                │             │
  │                   │ 5.从L2读取k1,k2的valueHash(作为基准)        │                │             │
  │                   │ 6.比对各实例L1哈希与L2哈希              │                │             │
  │                   │ 7.返回差异结果        │                      │                │             │
  │  ConsistencyResult│                      │                      │                │             │
  │◀─────────────────│                      │                      │                │             │
```

**关键设计点**：

- **触发方式**：手动触发（运维/开发调用管控 API），不自动定时执行。一致性检测对 Redis 有额外读写压力，自动跑可能影响正常业务；多数时候缓存一致，无需频繁检测
- **通信机制**：Redis Pub/Sub（Redisson RTopic），各实例启动时订阅 `l2cache:consistency:channel`，收到任务消息后实时响应，比定时轮询更及时且更轻量
- **各实例都参与上报**：因为一致性检测的目的是发现"不同实例 L1 缓存的差异"，每个实例都要上报自己的 L1 状态
- **上报内容为 valueHash 而非 value**：用 MD5 哈希代替原始值传输，减少网络开销，避免敏感数据泄露
- **结果存储与收集**：各实例将结果写入 Redis（key: `l2cache:consistency:result:{taskId}:{instanceId}`，TTL=10s），管控 API 等待 2-3s 后扫描收集
- **超时处理**：设置 5s 超时，未响应的实例标记为超时，返回部分结果 + 超时提示

### 6.2 核心类职责说明

- **MetricsRecorder**：埋点抽象接口，定义 recordHit/recordMiss/recordPenetrate/recordGet/recordPut/recordCacheSize/recordKeyAccess 等方法。core 默认注入 NoopMetricsRecorder
- **NoopMetricsRecorder**：空实现，所有方法空操作。保证未启用监控时零开销
- **KeyAccessStats**：本地内存维护 key 维度访问计数与 value 大小，提供 TopN 查询。基于 ConcurrentHashMap + 定时清理
- **MicrometerMetricsRecorder**：Micrometer 实现，通过 MeterRegistry 注册 Counter/Gauge/Timer
- **MetricsAutoConfiguration**：Spring Boot 自动配置，当 classpath 有 MeterRegistry 时注入 MicrometerMetricsRecorder
- **CacheManagerController**：扩展管控端点

## 9. 非功能性设计

### 9.1 一致性与并发控制

- **埋点并发安全**：MetricsRecorder 使用 Micrometer 内置线程安全计数器（Counter/Gauge 均为线程安全）
- **KeyAccessStats 并发**：基于 ConcurrentHashMap，TopN 排序使用并发快照（CopyOnWrite），避免锁竞争
- **一致性检测（两层对比，基于 Redis Pub/Sub 实时触发）**：
  - **触发机制**：管控 API 通过 Redis Pub/Sub（Redisson RTopic，复用已有 Redis 连接）发布检测任务到 `l2cache:consistency:channel`，各实例订阅该 Channel 实时响应，无需定时轮询，更实时且对实例更轻量
  - **数量对比（mode=count，cacheName 维度）**：各实例收到任务后上报 L1 的 key 数量，管控 API 比对各实例间及 L1 与 L2 的数量差异。适合快速扫描
  - **值对比-key 维度（mode=value&keys=k1,k2）**：调用方传入指定 key 列表，各实例计算这些 key 在 L1 中 value 的 MD5 哈希上报，管控 API 同时从 L2 读取 value 哈希，比对各实例 L1 哈希与 L2 哈希
  - **值对比-cacheName 维度（mode=value&sampleSize=100）**：不指定 key 时，自动从 L1 随机采样 sampleSize 个 key 做值对比，覆盖 cacheName 维度
  - 上报内容为 valueHash 而非 value 本身；各实例结果写入 Redis（TTL=10s），管控 API 等待 2-3s 后收集比对
  - 使用 Redis 已有连接和 Pub/Sub 能力，不新增中间件
- **幂等性**：管控 evict 操作幂等，清除不存在的 key 返回成功

### 9.2 性能与可用性

- **埋点性能**：
  - Micrometer Counter.increment() 为 AtomicLong CAS 操作，纳秒级，对 35W QPS 影响可忽略
  - KeyAccessStats 使用 ConcurrentHashMap.putIfAbsent + AtomicLong，无锁读路径
  - 大 key 估算异步执行（put 时提交到轻量线程池），不阻塞写路径
  - 埋点可通过配置 `metrics.enabled=false` 全局关闭，NoopMetricsRecorder 零开销
- **内存控制**：
  - KeyAccessStats 仅保留 TopN（默认 100），定期清理低频 key（默认 60s）
  - 一致性检测快照临时存储在 Redis，设置短 TTL（默认 30s）
- **降级**：埋点异常静默降级，catch 所有异常，不影响缓存读写

### 9.3 异常处理与恢复

- **埋点异常**：MetricsRecorder 所有方法 try-catch，异常仅 debug 日志，不抛出
- **管控端点异常**：统一异常处理，返回 ServiceResult.fail()，不暴露内部堆栈
- **一致性检测超时**：设置 5s 超时，超时返回部分结果 + 超时提示

### 9.4 监控与安全

- **监控设计**：本方案自身即监控系统，通过 Prometheus + Grafana 展示
- **安全性设计**：
  - 管控端点默认关闭，通过 `l2cache.metrics.management.enabled=true` 显式开启
  - 鉴权方案（参考性输出）：
    - 方案 A：复用 Spring Security，在 SecurityConfig 中对 `/l2cache/manager/**` 配置角色权限
    - 方案 B：自定义拦截器 + Token 校验，在 starter 中提供 `@L2CacheManagement` 注解标记需鉴权的端点
    - 方案 C：网络层隔离，管控端点仅暴露在内网，通过网关层做访问控制
  - 推荐方案 C（网络隔离）作为首期方案，方案 A 作为后期管理后台的鉴权基础

#### 10.1.6 一致性检测代码骨架

```java
/**
 * 一致性检测服务
 *
 * 基于 Redis Pub/Sub 实时触发，各实例订阅 channel 响应。
 */
public class ConsistencyCheckService {

    private final RedissonClient redissonClient;
    private final String channel = "l2cache:consistency:channel";

    /**
     * 触发检测（管控 API 调用）
     */
    public ConsistencyResult check(String cacheName, String mode, List<String> keys, int sampleSize) {
        String taskId = IdUtil.simpleUUID();
        // 1. 发布检测任务到 Redis Pub/Sub
        ConsistencyTask task = new ConsistencyTask(taskId, cacheName, mode, keys, sampleSize);
        RTopic topic = redissonClient.getTopic(channel);
        topic.publish(task);

        // 2. 等待 2-3s 收集各实例响应
        Thread.sleep(3000);

        // 3. 扫描 Redis 收集各实例结果
        // key: l2cache:consistency:result:{taskId}:{instanceId}
        Map<String, InstanceSnapshot> snapshots = collectResults(taskId);

        // 4. 从 L2(Redis) 读取基准值
        Map<String, String> l2Hashes = getL2Hashes(cacheName, keys);

        // 5. 比对各实例 L1 哈希与 L2 哈希
        return compare(snapshots, l2Hashes);
    }

    /**
     * 启动时订阅 channel（各实例调用）
     */
    public void subscribe() {
        RTopic topic = redissonClient.getTopic(channel);
        topic.addListener(ConsistencyTask.class, (channel, task) -> {
            // 收到任务后计算本实例 L1 的 valueHash 并写入 Redis
            Map<String, String> hashes = computeL1Hashes(task);
            String resultKey = "l2cache:consistency:result:" + task.getTaskId() + ":" + L2CacheConfig.INSTANCE_ID;
            redissonClient.getBucket(resultKey).set(hashes, 10, TimeUnit.SECONDS);
        });
    }
}
```
